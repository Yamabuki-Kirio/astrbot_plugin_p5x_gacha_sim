# 给 P5X 写模拟抽卡：需要准备什么

> 参照 `HoshiKurea/astrbot_plugin_ww_gacha_sim`（鸣潮模拟抽卡）做一个「女神异闻录：夜幕魅影」版本。
> 本文回答的是「先要准备什么」，不是「怎么实现」——后者已经有一部分跑在 `astrbot_plugin_p5x_gacha_sim/` 里了。

---

## 0. 结论先行

| 判断 | 说明 |
| --- | --- |
| **代码不是瓶颈** | 参考插件 9590 行 Python 里，真正跟「鸣潮」绑死的只有概率表、卡池表和渲染排版。机制层 200 行就能写完，本原型已经跑通。 |
| **素材才是大头** | 需要 **221 张立绘**（角色 + 专武）+ 若干卡池横幅。没有素材插件也能跑（自动出占位图），但「像不像那么回事」全靠这批图。 |
| **卡池表要人肉校对** | 谁在哪一期 UP、常驻池到底有哪 5 个 5★、每期轮换时间——这些没有任何接口能拿到，只能手工维护。 |
| **概率有一块是黑的** | 5★/4★/保底是公开的；**3★:2★ 的拆分官方没公示**，公开资料只写「2-3★ 人格面具 93%」。这一项要么接受近似，要么自己抽几千发实测。 |

一句话：**先备数据（卡池表 + 面具表），再备素材（221 张图），代码反而是最后才需要操心的。**

## 1. 参考插件拆解：抄什么、扔什么

克隆下来的实际体量：**44 个 py 文件 / 9590 行**，另有 webui 2107 行，素材 1.8 MB。

| 模块 | 行数 | 在鸣潮里干什么 | P5X 怎么处理 |
| --- | ---: | --- | --- |
| `main.py` | 876 | 指令组 `/wwg`、参数解析、图片发送 | **照抄骨架**，换指令名和卡池即可（已实现） |
| `src/gacha/gacha_mechanics.py` | 207 | 概率 / 软保底 / 硬保底 / 50-50 | **照抄语义，重写数值**（已实现，见 `src/core/mechanics.py`） |
| `src/gacha/gacha_flow.py` | 77 | 事务化十连 | 简化后并入 service（已实现） |
| `src/gacha/cardpool_manager.py` | 900+ | 卡池配置读写、校验、版本号 | P5X 池子类型不同，**重写**为 JSON + Registry（已实现，约 150 行） |
| `src/db/*` | 1200+ | SQLite 记录、迁移、并发写 | **砍掉迁移与旧身份认领**，3 张表够用（已实现，约 230 行） |
| `src/render/gacha_renderer.py` | 800 | 立绘排版、精灵图集、结果图 | P5X UI 完全不同，**重写**（已实现，约 300 行，无素材可退化） |
| `src/render/resource_loader.py` 等 | 900 | 远程拉图、缓存、代理、离线包 | **建议先不做**；等素材定稿再说 |
| `src/web/*` + `pages/admin/*` | 1300+ | AstrBot Plugin Pages 管理页 | **P3 再做**，前期改 JSON 重启更快 |
| `tests/*` | 1500+ | 运行时消息管线、资源、渲染测试 | 抄思路：机制层必须能脱离 AstrBot 单测 |

> 关键经验（值得直接继承）：**渲染失败绝不重抽**，先发文字再补图；**十连排序只影响展示**，入库保留真实顺序；**立绘缺失要能降级**而不是报错。这三条在参考插件里是花了版本迭代才磨出来的。

## 2. P5X 的规则数字（写进代码前必须确认的部分）

| 卡池 | 5★ | 4★ | 低阶 | 5★ 硬保底 | UP 规则 | 最坏得 UP | 单价 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 角色契约（限定） | 0.8% | 6.2% | 2-3★ 人格面具 93% | 80 抽 | 5★ 50% 为 UP，歪了下次必中 | **160 抽** | 150 晶珀 |
| 角色契约（常驻） | 0.8% | 6.2% | 同上 | 80 抽 | 无 UP | — | 150 晶珀 |
| 武器契约（限定） | 0.8%（其中 UP 0.4%） | 8.0% | 3★ 武器 91.2% | 70 抽 | 5★ 50% 为 UP，歪了下次必中 | **140 抽** | 100 晶珀 |
| 武器契约（常驻） | 0.8% | 8.0% | 同上 | 70 抽 | 无 UP | — | 100 晶珀 |

补充规则：

- **4★ 有独立保底**：每 10 抽必出 4★ 及以上（5★ 也算满足）。
- **保底跨池继承**：限定角色池换期不清零，武器池同理；限定与常驻分别计数。
- **常驻角色池 300 抽自选**一个 5★。
- **歪了就进大保底**：这次 5★ 不是 UP，下一次 5★ 必定是 UP，这个状态也跨池继承。

### 这些数字算出来是什么样

用本原型的引擎跑蒙特卡洛（每池 2 万次「抽到第一张 5★/UP」，脚本 `tools/simulate.py`）：

| 卡池 | 5★ 平均抽数 | 综合概率 | UP 平均抽数 | 中位数 |
| --- | ---: | ---: | ---: | ---: |
| 角色 | **59.16 抽**（理论 59.26） | 1.69% | 89.04 抽 | 80 抽 |
| 武器 | **53.73 抽**（理论 53.76） | 1.86% | 81.00 抽 | 70 抽 |

> 对照：角色池 0.8% + 80 抽硬保底，数学期望就是 `(1-0.992^80)/0.008 = 59.26`。**中位数 = 80**，也就是说一半以上的人要吃满保底——这是 0.8% 池子的正常体感，不是你写错了。
>
> 另一个容易误会的数字：**4★ 实际出货率约 12.3%，不是 6.2%**。6.2% 是「基础概率」，加上每 10 抽必出 4★ 的保底后，实测就是 12% 左右。写文档/做说明时别把这两个数混着用。


### ⚠ 还没确认的三件事

1. **3★ : 2★ 的拆分**。公开资料只有「2-3★ 人格面具 93%」。当前默认 3★ 3%、2★ 90%，**属于占位推断**，`data/banners.json` 里改 `rates` 即可。
2. **有没有软保底**。P5X 硬保底 80/70 是明确的，但「70 抽之后概率递增」这类机制没有任何官方说明。当前按「无软保底」建模（`soft_pity: []`）；参考插件支持软保底区间，需要的话改配置就行。
3. **国服 / 日服 / 国际服差异**。日服有「精准池」等本土化机制（NGA 有讨论），如果你要做的是国服，池子规则可能不同。

**建议**：把这几项做成 `data/banners.json` 里的显式字段，别写死在代码里。等有实测数据了改 JSON 重启即可。

## 3. 数据盘点：手上已经有什么

工作区里 `p5x-data-crawler/` 已经把角色和武器抓下来了（来源：lufel.net 社区数据 + 官方公告），本插件直接复用：

| 数据 | 数量 | 状态 |
| --- | ---: | --- |
| 角色（含中文名 / 属性 / 定位 / 稀有度 / 限定标记） | 72 | ✅ 可用 |
| ├ 5★ 角色 | 53 | ✅ |
| ├ 其中限定 5★ | 38 | ✅ |
| └ 4★ 角色 | 16 | ⚠ 偏低（52 个里只识别出 16 个 4★，其余是未上线或无稀有度） |
| 武器（5★ / 4★ 专武，含攻防血） | 140 | ✅ 可用 |
| 人格面具 2★ / 3★ | 0 | ❌ **用手写的 38 条占位顶着** |
| 3★ 武器 | 0 | ❌ **用手写的 12 条占位顶着** |
| 立绘 / 图标 | 0 | ❌ 全缺 |

### 还缺的（按阻塞程度排序）

1. **常驻池的官方名单**。现在用「非限定 5★」（15 个）近似，但官方常驻池只放 5 个 5★、12 个 4★。**这一项会直接影响抽卡体验**，必须人工确认。
2. **人格面具 2★/3★ 完整表**。38 条占位能跑，但抽出来全是「杰克灯笼」这种通用面具，玩家一眼看出是假的。
3. **3★ 武器表**。同上。
4. **每期 UP 的轮换表**（谁、什么时间、持续多久）。目前只生成了一个「最新限定角色」的示例池。
5. **立绘 / 横幅**，见下一节。

### 数据来源建议

| 想要的数据 | 去哪儿找 |
| --- | --- |
| 官方概率与池子公告 | `p5x.wanmei.com` 公告页（中文最权威） |
| 角色 / 武器数值 | 已有 lufel.net 抓取结果；官方 Wiki 补 |
| 常驻池名单 | 游戏内截图（卡池详情页会列全部候选） |
| 面具表 | 游戏内面具图鉴截图，或日服 wiki |
| UP 轮换历史 | 官方社媒公告，逐期手工补 |

> 游戏内截图是**最快也最准**的路子：把卡池详情页截下来，池子构成、概率、保底全在上面，比任何第三方攻略站都可靠。

## 4. 素材：221 张图，怎么备

跑 `python tools/report_coverage.py` 得到当前缺口：**4 个卡池共引用 221 个物品，缺立绘 221 张**。

命名规则（插件自动匹配，不用改代码）：

```
assets/portraits/char_SKULL·Starlight.png      ← 角色 char:SKULL·Starlight
assets/portraits/weapon_SKULL-weapon5-1.png    ← 武器 weapon:SKULL-weapon5-1
assets/banner/char_limited.jpg                 ← 卡池横幅，可选
```

| 项目 | 建议 |
| --- | --- |
| 格式 | 透明 PNG（或 WebP），长边 1024–1600 |
| 体积 | 单张 ≤ 2 MB；十连一次读 10 张，太大拖慢渲染 |
| 来源 | ①官方公告/社媒宣传图 ②自己截的图 ③官方素材站（若开服有） |
| 不要用 | 第三方 wiki 的汉化立绘、别人的整合包——版权和传播风险都在你身上 |
| 分阶段 | 先补 **5★ 角色 + 当期 UP 的专武**（约 20 张），其余用占位图，效果已经能看 |

**折中方案**：插件缺图时会画「稀有度色块 + 角色首字」的占位卡片（见 `output/demo_ten.jpg`）。先上线、后补图完全可行——这也正是参考插件「先发文字再补图」那套逻辑的延伸。

## 5. 环境与技术准备

| 项 | 要求 | 备注 |
| --- | --- | --- |
| AstrBot | ≥ 4.27.5 | 用到了 `@filter.command_group` 与 `StarTools.get_data_dir(name)` |
| Python | 3.12+ | 用了 `X \| None` 语法 |
| 依赖 | `Pillow >= 11.2.1` | 参考插件还要 `httpx`（拉远程立绘），本原型不联网拉图，**没有这个依赖** |
| 字体 | 系统需有中文字体 | Windows 自动找 `msyhbd.ttc`；Linux 装 `Noto Sans CJK`，否则中文变方块 |
| 存储 | SQLite（标准库） | 数据落在 `data/plugin_data/astrbot_plugin_p5x_gacha_sim/p5x_gacha.sqlite3` |
| 并发 | 抽卡要串行 | 「读保底 → 抽 → 写保底」必须加锁，否则并发会丢保底（已实现） |

**部署前检查清单**：

- [ ] `/p5x 卡池` 能列出 4 个池子
- [ ] `/p5x 十连` 出图且保底数字在涨
- [ ] 重启后保底没清零（SQLite 落盘）
- [ ] 把 `assets/portraits` 清空后仍能出图（占位降级）
- [ ] 群聊里 @ 机器人时指令不被当普通对话（检查 `wake_prefix` 配置）

## 8. 坑（踩过的和预判的）

1. **保底必须按 `pity_group` 存，不能按卡池 id**。限定池每期换 id，按 id 存等于每期清零，玩家会炸。已实现（`char` / `char_standard` / `weapon` / `weapon_standard` 四组）。
2. **十连展示可以按稀有度排序，入库必须按真实顺序**。否则「第 80 抽出货」这种记录会错乱。
3. **5★ 也要重置 4★ 保底**。5★ 出现时 `pity4` 一起清零，否则会出现「5★ 之后第 2 抽又蹦一个 4★」。
4. **素材缺失不能抛异常**。补图是长期工程，渲染器必须能降级。
5. **图片渲染失败不能重抽**。先发文字、再补图，参考插件在这上面栽过。
6. **官方随时改规则**。所有数字进 JSON，代码里不出现魔法数。
7. **版权**。素材来源合规、别打包别人的整合图、插件里写清楚「模拟抽卡，非官方」。
